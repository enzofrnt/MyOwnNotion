# État du code avant la refonte des bases

Audit du 27 septembre 2026. Ce document décrit le code actuel ; il ne tranche pas les choix produit en attente dans `spec.md`.

## Identités et hiérarchie

- `packages/domain/src/content/types.ts` définit `ItemKind` comme `page | folder | file`. Une base n'est donc pas encore un type canonique d'élément. `canContain` autorise actuellement tout enfant hiérarchique sous une page ou un dossier, sans règle propre aux bases.
- `packages/domain/src/content/hierarchy.ts` centralise la validation de création et de déplacement. L'ajout d'un type de base devra passer par cette frontière et par les projections serveur/client, plutôt que par une seule condition d'interface.
- La base actuelle est enregistrée séparément dans `databases` avec un identifiant qui est aussi celui d'un item. L'interface distingue une « page structurée » via un cache `structuredKindByItemId` dans `hierarchy-explorer.tsx`, pas via le `kind` canonique.
- `packages/database/src/repositories/lifecycle-repository.ts` met une branche hiérarchique à la corbeille et restaure ses placements. Le nouveau rôle de la base comme parent doit être vérifié avec ce cycle de vie et les vues qui pointent vers elle.

## Entrées, vues et édition

- `packages/database/src/mutations/database-commands.ts` crée aujourd'hui une entrée comme `page`. Sans placement explicite, elle n'apparaît pas dans l'arborescence ; si son parent demandé est la base, le code le transforme actuellement en racine. `packages/client-core/src/outbox/apply-to-projection.ts` reproduit cette logique localement. Le nouveau contrat « enfant de la base » exige une modification coordonnée de ces deux chemins.
- `packages/domain/src/databases/embeddings.ts` représente les vues intégrées par des emplacements dans la définition de source. Les vues de chaque emplacement existent déjà, mais leur cycle de vie est séparé de celui de l'item hôte.
- `apps/web/src/features/databases/page-databases.tsx` ajoute les vues après l'éditeur et affiche le bouton permanent « Ajouter une base ». Il ne représente pas encore une vue comme un bloc au point d'insertion du texte. `apps/web/src/features/editor/editor-menus/slash-menu.tsx` fournit déjà un précédent pour créer une sous-page et insérer son lien au même endroit.
- Le schéma structuré actuel accepte les propriétés titre, texte, nombre, date, statut, sélection, sélection multiple, case à cocher et relation. Il n'impose pas de limite arbitraire au nombre de propriétés dans `packages/domain/src/databases/types.ts`.

## Conséquences pour le plan

- La [documentation Notion sur les sources liées](https://www.notion.com/fr/help/data-sources-and-linked-databases) distingue le conteneur de base, les sources qu'il possède ou lie, et les vues. Une vue liée peut montrer une source externe dans le conteneur ; ses filtres et tris sont indépendants de ceux des autres vues. La [documentation des vues](https://www.notion.com/help/views-filters-and-sorts) décrit les onglets, leurs réglages propres et leur présence dans la navigation. Le propriétaire précise que l'intégration dans une page montre une seule vue à la fois.
- Le modèle visé ne doit pas confondre « changer la source affichée par une vue » avec « supprimer la source possédée par son conteneur ». Cette dernière reste conservée même si aucune vue ne l'affiche, jusqu'à suppression de son conteneur propriétaire.
- Décider si « vue de base » est un élément de hiérarchie, un bloc éditorial, ou les deux avant de modifier le vocabulaire canonique.
- Spécifier l'appartenance des descendants des dossiers présents dans une base et la règle d'interdiction des bases imbriquées, puis appliquer la même validation aux créations et déplacements.
- Concevoir l'insertion pleine page et l'insertion intégrée comme des opérations durables cohérentes entre hiérarchie et document, y compris hors ligne et après interruption.
- Le propriétaire autorise la remise à plat des migrations et l'effacement des anciennes bases et entrées de développement avant la V1. Documenter une procédure explicite de réinitialisation ; tester export, sauvegarde et synchronisation sur les nouvelles données.

## Essai direct dans l'application Notion

Le 27 septembre 2026, une base temporaire nommée « Test Codex sources et vues » a été créée dans l'espace privé du propriétaire afin de vérifier le cycle de vie des sources. L'essai a été fait dans l'interface de l'application Notion via Ordinateur ; la base reste disponible pour inspection.

1. La base neuve avait un seul onglet Table. Dans « Afficher les paramètres », l'action « Source Nouvelle base de données » était désactivée. Le menu contextuel de l'onglet montrait lui aussi une source désactivée.
2. « Dupliquer la vue » a créé un deuxième onglet Table. Dans ses paramètres, l'action « Source Test Codex sources et vues » était alors disponible.
3. La deuxième vue a été reliée à la source existante « Emmy ». Le conteneur a reçu un titre combinant son titre d'origine et « Vue de Emmy » ; son deuxième onglet montrait les propriétés et entrées d'Emmy. Le premier onglet montrait encore la source d'origine.
4. La première vue a ensuite été reliée à « Emmy » également. « Gérer les sources de données » affichait toujours « Test Codex sources et vues » sous « Source » et « Emmy — 2 vues » sous « Liées ». Cela confirme que la source possédée reste présente sans vue locale active.
5. La page « Base » du propriétaire montre une base intégrée « pongpgonzpongz » avec deux onglets Kanban dans l'application Notion. La règle souhaitée pour MyOwnNotion reste une seule vue par bloc intégré, selon les indications du propriétaire ; cette différence doit être explicitement validée avant le plan.

L'essai n'a pas testé la suppression ou la restauration d'une source, ni le déplacement d'une entrée avec restitution de ses propriétés. Ces règles viennent des décisions du propriétaire et devront être couvertes par les tests de la feature.

La [documentation officielle des sources de données](https://www.notion.com/en-gb/help/data-sources-and-linked-databases) confirme qu'un conteneur peut avoir plusieurs sources propres et liées, que les sources propres peuvent être déplacées et que les réglages des vues liées restent locaux. La [présentation officielle des bases](https://www.notion.com/help/intro-to-databases) confirme que les entrées sont des pages et que chaque vue garde ses réglages. La [documentation des propriétés](https://www.notion.com/help/database-properties) donne la gamme actuelle des types. Ces pages décrivent Notion ; elles n'étendent pas à elles seules le périmètre de MyOwnNotion.

### Différences tranchées pour MyOwnNotion

1. Une seule vue modifiable par bloc intégré, sans plusieurs onglets dans ce bloc.
2. Une source propre créée avec chaque page de base ; ses vues peuvent référencer des sources possédées ailleurs. Une deuxième source propre dans la même page et son déplacement indépendant restent hors de cette refonte.
3. **Tranché par le propriétaire** : la première refonte conserve Table, Kanban, Galerie, Liste et Calendrier ; les autres formats observés restent hors périmètre.
4. **Tranché par le propriétaire** : l'insertion d'une vue d'une source existante passe par une commande dédiée « Vue liée de base de données ».

Les tests complémentaires n'ont pas confirmé le comportement d'une vue liée lorsque sa source est mise à la corbeille ou purgée. La mise à la corbeille d'une source propre est une action distincte dans Notion, mais la politique d'avertissement et de restauration de MyOwnNotion reste définie par le propriétaire. Le sélecteur interne à un conteneur n'a pas proposé la seconde source propre du conteneur de test lors d'un essai, alors que le sélecteur de la commande `/vue` l'a proposée ; cette différence peut dépendre du contexte et ne suffit pas à établir une règle générale de disponibilité des sources.

## Audit du dépôt avant le plan d'implémentation

Recherche en lecture seule sur domaine/persistance, UI et import/export, le 27 septembre 2026.

| Décision | Raison observée dans le dépôt | Alternatives évaluées |
| --- | --- | --- |
| Deux types canoniques `database` et `database_view` et une source à ID distinct | `packages/domain/src/content/types.ts` n'a que page/folder/file. L'UI déduit aujourd'hui les bases par requête asynchrone et `0016_linked_databases.sql` a détaché les sources de la hiérarchie. Des types natifs rendent arbre, fil d'Ariane, corbeille et sync cohérents. | Garder des pages factices identifiées par une table latérale : ambiguïtés persistantes et chargement concurrent. |
| Une présentation distincte de la définition de source | L'actuelle `DatabaseDefinition` porte propriétés, vues et embeddings ensemble ; elle ne peut pas exprimer proprement deux vues du même conteneur pointant vers des sources différentes. | Ajouter `sourceId` aux vues de la même définition : conserverait la propriété des vues sous une source et compliquerait les vues liées sans source propre. |
| Entrée active = enfant direct du propriétaire, valeurs historiques par `(sourceId,entryId)` | `database_entries` maintient aujourd'hui une appartenance parallèle et `database.entry.create` place les entrées à la racine. La spec exige une seule vérité hiérarchique et la restitution après sortie/retour. | Dupliquer appartenance et placement avec réparation ultérieure : risque de dérive hors ligne et à l'import. |
| Bloc `databaseView` canonique dans le document | `page-databases.tsx` affiche actuellement les embeddings après l'éditeur avec « Ajouter une base » ; cette liste ne préserve ni position au curseur ni intégration dans le flux. BlockNote/ProseMirror, modèle de blocs et export doivent accepter le même bloc. | Garder une liste d'embeddings sous la page : ne satisfait pas l'insertion entre paragraphes. |
| Nouvelle migration avec garde et remise à zéro ciblée explicite | Le moteur applique les SQL numérotés ; modifier `0007`/`0016` rompt les installations déjà migrées. `dev:stack:reset` efface aussi fichiers et sauvegardes. | Réécrire les migrations historiques ou vider les tables automatiquement : effet caché ou perte plus large que les seules bases. |
| Import 028 adapté au placement propriétaire dès l'aperçu | `plan.ts` et `apply.ts` créent des sources cachées ; `markdown.ts` ignore les `.base`. L'aperçu, les IDs déterministes et la reprise doivent refléter le modèle final avant connexion à la cible. | Réparer les placements après import : peut créer cycles, doublons ou états intermédiaires durables. |

Les points d'entrée concrets sont `packages/domain/src/{content,databases,document,export}`, `packages/database/src/{mutations,repositories,schema}`, `packages/contracts/src/content-api.ts`, `packages/client-core/src/outbox/apply-to-projection.ts`, `apps/api/src/{routes,sync,backup,imports/notion}`, `apps/web/src/features/{editor,databases,hierarchy,navigation}`, `apps/web/src/services/{databases,local-content}`. Les anciens tests `tests/e2e/linked-databases.spec.ts` et `databases-schema.spec.ts` supposent le bouton permanent et doivent être réécrits, non simplement désactivés. Les cinq moteurs de rendu de vue peuvent rester, mais leur configuration doit être résolue par vue et source. La revue UI applique `ui-quality` et `lessons.md`.

## Session 2026-09-30

Le stockage actuel empêche plusieurs sources sur une même page : `databases.item_id` est la clé primaire, et `database_entries.database_id` référence cette clé. `ownedSourceIdFromItemId` fabrique un seul identifiant de source par page. Une page `database_view` est limitée à une vue par `validateDatabasePresentation`. Le bloc intégré charge une seule vue. Ces contraintes sont le travail de la phase 9 ; elles ne contredisent pas la décision produit du 30 septembre.
